# 意图评测工作流设计（2026-10-19）

## 目标与范围

把现有 Morgan ClawBench 从“手动录入两个模型回答并评分”的页面，扩展为可在线完成的评测工作台。第一批题目由 Morgan 提供和确认，主要考察模型能否理解多轮对话中最后的有效意图，并**完成用户实际要求的任务**。候选模型暂按 DeepSeek Flash、GLM-5.3-Flash、阶跃星辰 Step 5 Preview 展示；实际 API 模型 ID、密钥和费用待配置，报告记录真实调用版本。

本设计覆盖：Word 导入与逐题确认、模型先答、人工独立作答、意图核验、四档 GSB、可导出报告，以及可替换的自动答题入口。首版接收 `.docx` 和现有手动建题。旧版 `.doc`、扫描件 OCR、自动生成标准答案、公开访客评分和统一总分不在首版范围。

## 方案取舍

1. **推荐：现有 GitHub Pages + 私有数据仓库 + GitHub Actions。** 浏览器负责导入、确认、人工答题、复核和报告；私有仓库保存题目与运行结果；Actions 在后台调用模型 API。它沿用现有部署，模型密钥放在 Actions Secrets，网页不接触密钥。缺点是批量任务有启动延迟，仓库文件存储和 GitHub 权限不适合未来大规模多人协作。
2. **仅在浏览器直接调用模型 API。** 接入快，但需要把模型密钥交给浏览器，当前公开静态站点无法安全管理长期密钥，因此不采用。
3. **独立后端和数据库。** 更适合多人权限、队列与大规模数据，但增加部署和费用；当 GitHub 仓库式工作流到达规模或权限瓶颈时再迁移。

自动答题有两种输入通道，共用同一种运行结果格式：

- **平台直连**：在私有数据仓库配置各模型 API 的 Actions Secrets 和固定 provider/model 映射，网页发起一批运行，Actions 逐题调用并保存原始回答、状态、耗时和返回模型版本。未配置密钥时明确显示“待配置”，不假装运行成功。
- **用户 Agent 平台**：平台按给定 JSON 题目格式运行，返回或上传同格式答案；网页可导入结果文件。平台输出按题目 ID、题目版本、运行 ID 和模型标识匹配，缺题、重复、版本不符必须报错。将来可让 Agent 平台直接调用受限接口提交，首版先有可用的结果文件导入。

## 工作流

1. **导入与审核。** 用户在网页选择 `.docx`。本地解析文字和显式题号、轮次，生成草稿预览；标出无法确定的切题边界、缺号、重复号、表格或图片依赖。用户可以逐题修改标题、对话轮次、能力维度和“最终意图卡”，明确保留要求、被后文覆盖的要求、缺失材料与可接受完成方式，再确认入库。原始 Word 默认不上传；私有仓库只存结构化题目和来源文件名、哈希等追溯信息。解析不能确定时留在草稿，不能自动批准或自动运行。
2. **冻结一次评测。** 只选已确认题目，记录题目 ID、版本、意图卡版本及其快照、模型清单、运行 ID、时间。后续改题不改变既有运行；新题目版本需要新运行。题目正文发给模型，隐藏人工意图卡和答案。
3. **模型先完成任务。** 每个模型每题只生成一份固定原始答案，供后续全部比较复用。成功、失败、超时、缺密钥分别记录；重试生成新 attempt，不覆盖原始 attempt。用户可在运行前选择 API 直连或 Agent 平台结果导入。
4. **人工独立作答。** 模型答题后，用户在网页看到同一份原始多轮对话，独立完成实际任务。提交前界面不展示任何模型答案或机器评分。提交后锁定原稿和时间；更改形成新 revision，报告标明使用的版本。人工答案是对照样本，不自动当作唯一标准答案。
5. **意图核验与 GSB。** 用户查看预先确认的意图卡，对人工和每个模型回答分别标注最终任务及保留要求是否完成，结论为“通过 / 部分通过 / 未通过 / 不可评”，留下依据。三模型每题形成三个两两比较，左右随机并记录映射，四档 GSB 保持“左边好 / 右边好 / 一样好 / 一样差”。可单独比较“模型 vs 人工答案”，但不混入模型间榜单。可选 AI 评审也使用同一核验与 GSB 结构，保存原始机器判断；人工裁定另存，不能覆盖原始记录。
6. **报告。** 网页生成可浏览、可下载的报告（Markdown/JSON，并提供打印视图）。包括题库与运行版本、模型及调用信息、样本量和排除原因、调用成功率、最终意图完成率、四档 GSB 分布及相对比较分、人与模型的任务结果一致率、逐题证据与失败案例。若启用 AI 评审，另列其与人工四档 GSB 的完全一致率。报告可追溯到固定运行和评分版本。

## 指标口径

- **最终意图完成率**：某模型人工核验为“通过”的可评题数 ÷ 该模型已完成人工核验的可评题数；部分通过另列。不可评、调用失败和未审核不进入质量分母，分别显示数量。
- **GSB 相对比较分**：胜 1、负 0、一样好或一样差各 0.5；两个平局类别必须分别展示。三模型各题复用原始答案，不能在每场对比中重新生成。它不等于绝对准确率。
- **人机任务结果一致率**：同题人工答案和该模型答案在人工核验的“通过 / 部分通过 / 未通过”档位相同的题数 ÷ 双方均有可评核验的题数。报告同时显示“双通过、仅人工通过、仅模型通过、双未通过”等分布，避免双方都失败造成虚高解读。文本相似度不作为意图一致率。
- **AI 评分与人工评分一致率**：如启用 AI 评审，则同一对比中机器与人工四档 GSB 完全相同的场数 ÷ 双方都完成评分的场数。它与上面的人机任务结果一致率是不同指标。
- 所有比率展示分子、分母；按模型、题目维度展示，不合成为一个总分。题库覆盖率、API 成功率与质量指标分列。

## 页面与数据边界

现有页面保留题库和模型结果，导航调整为“题库导入 / 运行 / 人工作答 / 核验与 GSB / 报告”。从旧 `intent-benchmark/state.json` 加载题目和已有 GSB 记录，兼容旧数据；新增运行、人工答案、核验和报告按运行 ID 分文件保存到私有仓库，避免一份 JSON 无限膨胀。前端只从当前连接的私有仓库读写数据。题目和回答作为纯文本呈现，不能作为 HTML 或脚本执行。

最小数据单元：`QuestionSnapshot`（题目、轮次、版本、来源、意图卡）、`Run`（模型及题目快照、状态）、`Answer`（题目、模型或人工、原文、版本、来源、时间和 attempt）、`IntentReview`（逐要求项和总判定）、`Comparison`（两份固定答案、左右映射、四档结论、评审来源）、`Report`（口径、统计和原始记录引用）。保存动作使用 GitHub 文件 SHA 防止并发覆盖；失败给出可重试提示，不把未成功保存的内容计入结果。

## 安全、异常与验收

- GitHub PAT 只用于连接既有私有数据仓库，并仅留在页面内存。模型 API 密钥只放私有仓库的 Actions Secrets；不能写入 GitHub Pages、题目、导出文件或日志。浏览器页面仅在 HTTPS 提供 PAT 输入。评测数据与原始 Word 不发布到公开站点。
- `.docx` 在浏览器本地处理，限制体积；无法读取、扫描件、自动编号丢失、附件依赖和模糊切题均给出具体告警，并允许手工修正。网页不自动运行未确认题。模型调用对固定 provider 和模型配置做白名单限制，题目文本只作为数据传入。
- 可用一份含多轮和后续修正的 `.docx` 导入、手工修正并确认；冻结运行后，模型先给出实际任务答案，人工在看不到模型答案时提交；同一模型回答用于所有配对；人工完成核验及四档 GSB 后可导出含原始依据的报告。
- 在没有 API Key 的情况下，Agent 平台结果导入仍能走通全流程；API 直连入口明确说明待配置。首次上线用虚构样例和假 provider 验证状态流转、失败处理、版本隔离和导出，不能把假运行混入正式成绩。

## 实施顺序

先完成结构化题目与 `.docx` 预览、固定运行和人工独立作答；再完成外部 Agent 结果导入、意图核验、GSB 与报告；最后接 GitHub Actions 的模型 API 适配器。每段完成后用同一组虚构题验证端到端流程。真实题目和真实 API 密钥由用户之后提供。
